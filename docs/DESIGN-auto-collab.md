# 設計：有邊界的自動協作（可選主導者）

## 2026-10-11 Local 執行後端更新

原 Local 角色已改由 Hermes CLI 執行，可選作主導、實作或第二意見；既有交接、驗收、run correlation 與步數限制沿用。Hermes 以穩定 Workspace alias 對應 native session，成功 result 加 process exit 0 才視為完成。Hermes 的工具核准使用自身單次模式設定，不提供 Workspace 逐次核准橋接。詳細操作、600 秒預設與既有 900 秒 step timeout 的關係見 [HERMES](HERMES.md)。下方舊 Local harness 描述保留為歷史。

## 2026-10-09 操作邏輯修正

本節取代下方「參與者須共用 project／task」及「啟動即切到唯讀總覽」的早期限制。各參與者沿用自己的 Project／Session，任務紀錄可以不同；啟動前呈現綁定預覽。Run 分別固定各 instance 的 adapter、project、task 與 session，傳送契約與回覆查詢使用接收者的紀錄容器。主導者的容器保存 run 稽核事件；切換無關紀錄不暫停 run，改變參與者綁定則暫停。

啟動後保留工作台，只鎖定參與者；其他 Agent 可以獨立聊天、切專案或開 session。唯讀總覽仍可自行開啟。停止全部 Agent 或關閉視窗時先停止派工，再要求後端取消，防止取消途中啟動下一步。核准、回覆關聯、執行上限與不確定傳送不重送的規則仍適用。

## 2026-10-09 產品目標追加：動態 Agent 與同類協作

使用者確認需要自行新增多個 Agent 視窗、各自固定 project／session、獨立工作或協作，並且整組可以全部使用 Claude。下方 Claude／Codex 對向派工表描述現有實作，不再代表未來參與者的限制。

已實作第一階段：provider 與 Agent instance 分離，支援手動新增 Claude／Codex／Local 視窗，按 instance 路由；自動協作可分別選擇主導者與實作者，包括兩個 Claude。程式介面使用 `lead=<instance_id>` 與 `implementer=<instance_id>`，兩者必須不同。動態參與者沿用其 provider 的逾時預設，也能以 instance ID 覆寫測試／程式設定。

目前仍是一位主導者、一位實作者與原有可選複核流程；多位實作者平行排程與 Agent 自行新增隊員尚未實作。同 provider 的隔離與全 Claude 的雙 Agent 協作有離線測試，尚未進行真實後端驗收。詳細訪談決策、GitHub 參考與待確認政策見 [UI-REFRESH.md](UI-REFRESH.md)。

## 2026-10-09 更新：預設由 Claude 直接派工與驗收

依 Ryan 本次確認的工作方式，預設流程調整為：

```text
Claude 派工 → Codex 實作與回報 → Claude 驗收
                  ↑                │
                  └─ 要求修正 ──────┘
                                   └─ APPROVED → 完成
```

- 只有 Claude 的 `APPROVED` 會完成整次協作；Codex 的 `IMPLEMENTED` 只是進入驗收。
- 開始時可選擇「加入 G8毛」，使用下方保留的三方複核流程。直接模式不需要 Dot 連線、授權或收發。
- Local LLM 仍可選第二意見或替代實作者；第二意見失敗會附註後交回 Claude／G8毛，最終判定仍屬 Claude。
- 每次明確啟動後，在指定 project / task / session 內自動交接；一般交接不需再確認。工具核准仍由使用者決定。
- 啟動時設定回合、步數與整次有效時間上限，預設為 **3 回合、24 步、60 分鐘**。有效時間含 session 準備與請求等待，不含已觀測到的工具核准等待。原有單步 timeout 仍有效。
- 步數計算已建立的交接請求，包含第一步派工；達上限後不再建立下一步。達時間上限會停止自動路由、令尚未送出的延遲呼叫失效；已被後端接受的工作不保證立即取消，需查看角色結果或使用角色停止操作。
- 保留完整回覆封套、run / step / nonce 關聯、session 綁定、取消擁有權與不確定傳送不重送等既有限制。重啟不自動恢復執行。
- 啟動即開啟新的 Monitor 總覽。可查看目前負責角色、進度、待核准數、每個角色自己的 project / task / session、規則與最近 10 筆交接紀錄。按角色卡片回到對話處理核准；也保留原本唯讀對話／legacy 紀錄入口。
- Monitor 只讀取 Workspace 本機資料；對話同步與既有 legacy 讀取沿用原機制。Monitor 不會自行連線、探索原生 session、送訊息或核准工具。
- 角色的唯讀審查是 prompt 約定，並非作業系統層級的權限隔離；後端權限與工具核准仍決定實際能力。

## §1 目標

Ryan 給一個任務之後，三個角色自己來回把它做完，不需要每一步都按「轉交」：

| 角色 | 在自動流程中的職責 | 能不能碰專案檔案 |
| --- | --- | --- |
| Claude | 規劃、最終審查 | 只讀（提示中明確要求不修改） |
| G8毛 | **傳輸**：把上一位的產出整理成給下一位的交接訊息；**自己審查一次**：先給出通過或退回的判定 | 不能改這台電腦的檔案；可自行到 GitHub 查看 |
| Codex | 實作 | 可以 |

Local LLM 預設不參與，開始時可以選擇讓它加入，有兩種角色：

- **第二意見**：Codex 實作完之後，由 Local LLM 以唯讀方式檢查專案資料夾並給出意見，意見會附在交給 G8毛 審查的內容後面。它是參考性質：逾時、出錯、斷線或沒照格式回覆時，流程會記錄「未提供意見」並繼續，不會因此停下來。
- **擔任實作者**：取代 Codex 做實作，這時不需要連線 Codex。它改檔時仍需要你在面板上核准。

## §2 流程

```
使用者輸入任務
   │
   ▼
[A] Claude 規劃 ──────────────► 計畫 P
   │
   ▼
[B] G8毛 審查計畫並轉寫成實作交接單
   │   判定 REVISE ──► 把意見送回 [A]（算一回合）
   │   判定 PASS
   ▼
[C] Codex 依交接單實作 ───────► 實作回報 R
   │
   ▼
[D] G8毛 審查回報（附 git 變更摘要），轉寫成審查請求
   │
   ▼
[E] Claude 最終審查（可讀專案）
       判定 APPROVED ──────────► 結束
       判定 CHANGES_REQUESTED ─► 意見經 [B] 送回 Codex（算一回合）
```

每則送出的訊息都用固定的信封格式，要求對方的回覆**第一個非空白行**必須完整是 `VERDICT: <值>`。
允許整行粗體 `**VERDICT: <值>**`、全形冒號及周圍空白；不接受前言後的判定、引用／程式碼區塊、部分 token 或同一行附加說明。
讀不到合法判定時不交接；有完成訊號的角色會暫停，G8毛 因無完成訊號仍依既定逾時規則暫停，不猜測。

上一階段的交接正文上限為 12,000 字元（不含固定信封及原始任務）。超過時暫停，不截斷、不讀取下一角色或送出新訊息；完整來源回覆保留在原對話紀錄。
Local LLM 第二意見與實作回報合併後也適用此上限，不能靜默丟棄其中一份。使用者須整理出完整、較短的交接後再明確開始新的執行。

## §3 邊界（全部都是硬性的）

1. **只在使用者按下「開始」後執行**，一次只跑一個任務。程式啟動時永遠不會自動開始，設定也不會記住「自動模式開啟」。
2. **回合上限**：預設 3，可設 1–10。到上限就停下來並回報目前狀態。
3. **每一步的等待上限**：Claude 預設 15 分鐘，G8毛 預設 20 分鐘，Codex 30 分鐘。逾時即暫停。
4. **工具核准永遠不自動**。任一角色出現核准請求時流程暫停，等使用者在面板上核准或拒絕後才繼續。
5. **任何錯誤即暫停**：連線中斷、後端回錯誤、訊息被安全過濾攔下，都不重試超過一次。
6. **隨時可停**：執行期間畫面上固定有「停止」按鈕，按下後不再送出任何新訊息，並對正在回覆的角色送出取消（G8毛 不支援取消，只能等它回完）。
7. **不切換專案或任務**：執行期間鎖住專案／任務切換，避免訊息送進錯的對話。
8. **全程留紀錄**：每一步寫入既有的 handoffs 與 events，時間線看得到完整經過，可匯出。

## §4 G8毛 的特殊處理

G8毛 是非官方整合，現在的設計是「每個動作都要人按一次同意」、而且明文寫著不輪詢、不轉送。自動流程必須放寬這兩點：

- **一次性的執行授權**：開始時跳出一個對話框，完整顯示既有的揭露文字，並寫明這次執行最多會對 G8毛 送出幾則訊息、多久讀取一次回覆。使用者同意後，只在這一次執行期間有效，執行結束或停止時立即失效。
- **輪詢讀取回覆**：送出後每 10 秒讀一次，直到出現新的 G8毛 回覆或逾時。這次執行對 G8毛 的總請求數有上限（400），到上限即暫停。
- 手動操作的單次同意機制保持原樣，不受影響。

**帳號風險**（需要 Ryan 明確接受）：這條路是用你的 ChatGPT 登入憑證呼叫非公開介面。手動偶爾用和程式自動連續呼叫，在對方眼中是不同的行為，有被限流或帳號受限的可能。我無法評估機率，也無法替你降低到零。

## §5 已知限制

- **G8毛 透過 GitHub 看程式碼**。它有自己的虛擬電腦，但看不到本機尚未 push 的變更。早期設計要求先 commit / push；此要求已由交接安全規則取代：commit、push、發布必須由原始任務明確授權，協作啟動本身不授權發布。未發布時須如實回報 G8毛 無法獨立驗證的範圍。
- **Claude 和 Codex 共用同一個資料夾**。流程靠提示要求 Claude 不改檔來避免互相覆蓋，這是約定而不是強制。要強制需要另外做 worktree 隔離，不在這一版。
- **費用**：G8毛 模式第一回合通常含 Claude 兩次、Codex 一次、G8毛 兩次請求；直接模式省略 G8毛。回合、步數、有效時間限制執行量，但不是 token 或金額預算。
- **判定靠文字約定**。模型偶爾會不照格式回，那時流程會暫停請你決定。

## §7 驗收（離線、用替身 adapter）

1. 正常路徑：A→B→C→D→E 一輪通過，五則訊息依序送給正確的角色，內容含上一步的回覆。
2. [B] 判定 REVISE：訊息回到 Claude，不送 Codex。
3. [E] 判定 CHANGES_REQUESTED：經 G8毛 回到 Codex；達回合上限時停止，之後不再有任何送出。
4. 回覆缺少合法判定：暫停，不送下一步。
5. 執行中出現核准請求：暫停；核准後繼續；全程沒有任何自動核准的呼叫。
6. 按停止：之後零送出；對 Claude／Codex 有送取消。
7. 任一步逾時、任一 adapter 丟錯：暫停並顯示原因。
8. G8毛 授權：未授權時自動送出被拒；授權期間可送與讀；執行結束後再呼叫被拒；請求數到上限即暫停。
9. 程式啟動與一般輪詢期間，沒有任何 adapter 被呼叫（既有測試維持通過）。
10. 既有測試基準不退步；提到「自動協作關閉」文字的既有斷言若需調整，逐條列出。

真實後端的驗收另外做：先用一個只需回覆文字的小任務跑一輪，確認三方真的接得起來，再試會改檔的任務。
